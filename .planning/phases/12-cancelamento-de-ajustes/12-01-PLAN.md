<objective>
Estender o cancelamento de lançamento (Phase 11, hoje só `tipo='pagamento'`) para cobrir também `tipo='acrescimo'` e `tipo='desconto'`, "da mesma maneira que foi feito para os pagamentos" — pedido explícito do usuário logo após a Phase 11 fechar. `tipo='destrava'` fica deliberadamente fora (D-01, 12-CONTEXT.md): é um registro de auditoria, não um valor lançado por engano, e apagá-lo enfraqueceria CONCIL-04.

Este é o slice mais fino que atravessa toda a camada que a fase toca — Server Action, ponte de query, diálogo, e a tela existente que precisa saber sobre o `tipo` de cada lançamento: a Task 1 prova a arquitetura ponta a ponta para os três tipos elegíveis (clique → confirmação com rótulo certo → DELETE condicionado a um allowlist → recálculo de status → tela atualizada), com a trava de conciliada valendo nos dois lados (UI e servidor) e o allowlist do servidor nunca incluindo `destrava`. A Task 2 fecha a fase atualizando `docs/data-model.md` para refletir o escopo ampliado — sem criar uma "terceira exceção" nova, porque é a mesma exceção da Phase 11, só maior.

**Decisão de nomenclatura (Claude's Discretion, 12-CONTEXT.md):** este plano opta por renomear `cancelarPagamentoAction`/`cancelarPagamento`/`CancelarPagamentoDialog`/`cancelar-pagamento-dialog.tsx` para `cancelarLancamentoAction`/`cancelarLancamento`/`CancelarLancamentoDialog`/`cancelar-lancamento-dialog.tsx`, em vez de manter o nome antigo. Motivo: os quatro símbolos hoje descrevem "pagamento" mas passam a cobrir três tipos — manter o nome antigo criaria uma dessincronia semântica permanente entre nome e comportamento. Escopo do rename confirmado por grep antes de planejar: exatamente 4 arquivos em `web/src` referenciam esses símbolos (`actions.ts`, `queries.ts`, o próprio arquivo do diálogo, `parcela-historico-sheet.tsx`) — todos já dentro do escopo desta fase, risco contido.

**Decisão de mensagem de erro genérica (server-side):** as strings `acao` passadas para `erroDoBanco()`/`semLinhas()` dentro da Server Action hoje dizem `"cancelar o pagamento"`. Depois do widening, um erro genérico de banco ao cancelar um acréscimo mostraria essa frase errada ("cancelar o pagamento" para um acréscimo). Este plano troca as duas ocorrências para `"cancelar o lançamento"` (tipo-neutro, natural nos três casos) — o texto tipo-específico ("Não foi possível cancelar o acréscimo...") continua existindo no fallback client-side do diálogo (`cancelar-lancamento-dialog.tsx`), usado quando o erro não é uma instância de `Error` vinda do servidor.

**Nota sobre CANAJU-01..04 e o probe de edge determinístico:** o probe rodado pelo orquestrador classificou as quatro requisições como `unclassified` (nenhum sinal de fronteira/nulo/formato — esperado para requisitos comportamentais de UI como estes). Em vez de deixá-las como suposição sinalizada, este plano resolve as quatro explicitamente a partir de 12-CONTEXT.md/12-PATTERNS.md, que já dão critério de aceite concreto e verificável para cada uma (ver `must_haves.truths` acima) — caminho permitido pelo protocolo de fallback quando o requisito já está bem especificado por outra fonte.

**Nota sobre o checkpoint de reversibilidade:** D-02 (12-CONTEXT.md, herdado de D-01 da Phase 11) é `one-way` — apagar não deixa rastro de quem cancelou o quê. Este plano NÃO insere um `checkpoint:decision` novo porque o usuário já confirmou esse exato trade-off na Phase 11 e pediu explicitamente para repetir "da mesma maneira" nesta fase — a porta já foi atravessada com consentimento registrado duas vezes.
