**1. `web/src/lib/kanban/actions.ts`** — na seção de helpers de validação, logo abaixo de
`numeroFinito()`, adicione `booleano(valor: unknown, campo: string)`: devolve
`` `${campo} inválido.` `` quando `typeof valor !== "boolean"`, senão `null`. Mesma forma de
`numeroFinito`.

Na seção **Imóveis**, logo depois de `deleteCardAction` e antes do comentário da seção Alertas,
adicione `setCardAtivoAction(cardId: string, ativo: boolean): Promise<ActionResult>`, espelhando
`moveCardAction` linha por linha: `requireUser()` primeiro; valide com
`id(cardId, "Imóvel") ?? booleano(ativo, "Situação do contrato")`; grave com
`.from("cards").update({ ativo }).eq("id", cardId).select("id")`; em erro,
`erroDoBanco(error.code, "atualizar o imóvel")`; em zero linhas, `semLinhas("atualizar o imóvel")`;
senão `{ ok: true, data: undefined }`. O `update` grava **somente** `{ ativo }` — nenhum outro campo
do card entra no objeto, e isso é o que implementa D-10 (nenhuma parcela, nenhuma outra coluna é
tocada por este caminho).

**2. `web/src/lib/kanban/queries.ts`** — importe `setCardAtivoAction` junto dos demais imports de
`./actions`. Adicione a função-ponte `setCardAtivo(id: string, ativo: boolean)` que devolve
`unwrap(setCardAtivoAction(id, ativo))`, no mesmo estilo de `moveCard`.

**3. `web/src/components/kanban/card-item.tsx`** — duas mudanças:
- Adicione `onToggleAtivo: (id: string, ativo: boolean) => void` ao tipo de props de `CardItem`,
  logo depois de `onUpdate`.
- Troque `<p className="mt-2 text-sm font-semibold text-primary">{formatCurrency(card.valor)}</p>`
  por `<div className="mt-2 flex items-center justify-between gap-2">` contendo esse mesmo `<p>`
  (inalterado) e, ao lado, um `<button type="button">` novo. O botão recebe `onPointerDown`,
  `onMouseDown` e `onClick` chamando `event.stopPropagation()` cada um — a mesma tripla que o
  `AlertDialogTrigger` do botão de excluir já usa logo acima, necessária pelo mesmo motivo: o `div`
  pai tem `{...attributes} {...listeners}` do dnd-kit e `onClick={() => setDetailOpen(true)}`, então
  sem a tripla o clique no pill tanto abriria o modal de detalhes quanto poderia iniciar um arraste.
  Dentro do `onClick`, depois do `stopPropagation()`, chame `onToggleAtivo(card.id, !card.ativo)`.
  Classes do botão: `rounded-full border px-2 py-1 text-xs font-semibold transition-colors` mais,
  condicional a `card.ativo`: `border-primary/40 bg-primary/10 text-primary` quando ativo,
  `border-border bg-muted text-muted-foreground` quando inativo. `aria-label` é o inverso do rótulo
  mostrado — descreve a ação que o clique vai fazer, não o estado atual:
  `` `Marcar ${card.endereco} como inativo` `` quando `card.ativo` é verdadeiro,
  `` `Marcar ${card.endereco} como ativo` `` quando falso. O conteúdo visível do botão é o estado
  atual: `{card.ativo ? "Ativo" : "Inativo"}`. Nenhum ícone — a palavra é o sinal inteiro (UI-SPEC:
  "kept intentionally quiet so it doesn't compete visually with `valor`").

**4. `web/src/components/kanban/column.tsx`** — adicione `onToggleAtivo: (id: string, ativo: boolean) => void`

`<CardItem onToggleAtivo={onToggleAtivo} ... />` sem nenhuma transformação — o mesmo fio direto que

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| navegador → Server Action `setCardAtivoAction` | clique otimista na tela dispara uma chamada de servidor autenticada por cookie de sessão |
| Server Action → PostgREST/Supabase | `UPDATE public.cards SET ativo = ...` com o JWT da sessão do usuário; o RLS de `cards` (já existente desde a Phase 1, via `is_team_member()`) é a barreira final |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-09 | Elevation of Privilege | `setCardAtivoAction` (`lib/kanban/actions.ts`) | high | mitigate | A função roda com o cliente Supabase de sessão do usuário via `requireUser()`/`createClient()` — nunca `service_role`. Verificado por asserção de fonte: zero ocorrência de `service_role` no arquivo. Se esta camada tiver um bug de autorização, o RLS de `cards` ainda barra o UPDATE por baixo |
| T-05-10 | Tampering | `cardId` arbitrário vindo do cliente | medium | mitigate | O UPDATE é filtrado por `.eq("id", cardId)` e pela policy de RLS de `cards`: um `cardId` fora do que a allowlist enxerga devolve zero linhas afetadas, tratado como `semLinhas()` — nunca uma escrita parcial ou indevida, e nunca um erro cru repassado ao cliente |
| T-05-11 | Information Disclosure | caminho de erro de `setCardAtivoAction` | medium | mitigate | Erros do Postgres passam por `erroDoBanco()`/`semLinhas()`, a mesma tradução já usada por `moveCardAction`/`deleteCardAction` no mesmo arquivo — nenhuma mensagem crua do banco chega ao navegador |
| T-05-12 | Tampering | ausência de diálogo de confirmação no toggle (D-09) | low | accept | Decisão de produto deliberada: a ação é reversível com um segundo clique e a Server Action só grava a coluna `ativo` (D-10), sem cascata — o custo de um clique acidental é baixo, então fricção extra (diálogo) foi conscientemente descartada, não esquecida |
| T-05-SC | Tampering | npm/pip/cargo installs | low | accept | Este plano não instala nenhum pacote — `web/package.json` não é modificado por nenhuma task. Todos os componentes usados (`button`, ícones) já estão instalados |
</threat_model>
