# Phase 6.1: Consulta financeira e geração por período - Context

**Gathered:** 2026-08-18
**Status:** Ready for planning
**Source:** Derived directly from a live conversation with the user, triggered by their feedback after testing Phase 6 in production. Confirmed via a navigable sketch (`.planning/sketches/001-consulta-financeiro/`, variant B chosen) and a follow-up round of clarifying questions. <domain>
## Phase Boundary

This phase makes two independent but co-requested changes to the Financeiro tab built in Phases 5/6:

1. **A search/filter layer replacing the "show everything" default** — the Mês atual/Próximo mês switcher (Phase 5, FINUI-02) is removed. The tab now defaults to "vencendo hoje" (parcelas due today), with an optional filter panel (proprietário, inquilino, período, ID do contrato) for anything else.
2. **A new parcela-generation rule** — contracts with both `periodo_inicio` and `periodo_fim` set now get **all** months of their period generated, including already-past ones (retroactive/backfill). Contracts with only one date, or neither, keep the Phase 5 behavior (current + next month only).

These two changes are bundled into one phase because they were requested together and the filter UI is what makes a full-period-generated contract (many rows, spanning many months) actually usable — without filters, a 12-month-backfilled contract would flood the "vencendo hoje" default view's neighbor states.

Also in scope: a new sequential contract ID (`#1`, `#2`, `#3`…), needed as a filter field and requested to appear on the Board card too.

Explicitly NOT in scope:
- Conciliar/destravar — Phase 7, unaffected by this phase
- Relatórios financeiros — Phase 8. Note the overlap: Phase 8's FINREL-05 already plans "filtros combináveis por imóvel, proprietário e período" for the read-only Relatórios tab. That is a **different surface** (reports) from this phase's filters (the action-taking Financeiro tab). Do not merge them or assume this phase satisfies FINREL-05.
- Bank statement import / real conciliação bancária — the user explicitly reconfirmed this is NOT what they meant by "conciliação"; Phase 7's manual-lock design stands as originally decided.
- A cap or pagination on how many parcelas a single very-long contract can backfill — not requested; if the pre-flight query (see Open Questions / Claude's Discretion) reveals an outlier, surface it before building, don't silently cap it.

Requirements: **CONTRATO-03, PARCELA-05, PARCELA-06, CONSULTA-01, CONSULTA-02**
</domain>

<decisions>
## Implementation Decisions

### Default view and filters — settled, sketch-validated

- **D-01:** The Mês atual/Próximo mês segmented control (Phase 5's `MesSwitcher`/`FinanceiroView`) is **removed**, not hidden or kept as an option. This is a deliberate replacement, confirmed twice: once in the initial feedback, once explicitly in the follow-up AskUserQuestion ("Substitui — recomendado").
- **D-02:** Default view (no filter applied): parcelas whose `vencimento` equals today's date (server-pinned `hojeISO`, same pattern already used everywhere in this codebase — see `web/src/app/(app)/relatorios/page.tsx` and `financeiro/page.tsx`). NOT "this week", NOT "this month" — exactly today.
- **D-03:** Filter fields: **proprietário** (text, partial match), **inquilino** (text, partial match), **período** (a month or date range — sketch used a single `<input type="month">`; exact shape is Claude's discretion, see below), **ID do contrato** (the new sequential ID, exact or partial match — Claude's discretion). All four are optional; only filled-in fields narrow the query. Filters combine with logical AND (validated in the sketch: filtering by proprietário AND ID together narrows further, doesn't OR).
- **D-04:** Applying any filter **replaces** the default "vencendo hoje" view with the filtered result set — there is no state where both are shown together. Clearing all filters returns to "vencendo hoje".
- **D-05 (sketch, variant B):** Filters live behind a "Filtrar" trigger (button/icon), collapsed by default — not an always-visible dense bar. Keeps the tab visually calm on the common case (checking what's due today) and only surfaces the filter form when the user actually needs it. See `.planning/sketches/001-consulta-financeiro/index.html`, variant B, for the exact interaction (toggle expands/collapses a panel with the 4 fields + Consultar/Limpar buttons).
- **D-06:** Selecting/finding a parcela in the filtered results must still lead to the existing, already-approved Pagamento/Ajustar/Histórico actions (Phase 6) — this phase does not redesign those, only the path to reach a parcela.

### Contract sequential ID — settled

- **D-07:** New field, auto-assigned, sequential (`#1`, `#2`, `#3`…) — user confirmed "Número sequencial automático" explicitly over alternative phrasings.
- **D-08:** Visible in **two** places: the Financeiro consulta (as a column/pill, per the sketch's `.id-pill` treatment) AND the Board card (user confirmed this explicitly, not just Financeiro). The card placement/visual treatment is Claude's discretion at the UI-SPEC stage, but it must not compete with the card's existing focal point (`valor`) per the Phase 5 UI-SPEC's established hierarchy rules — treat it the same weight class as a secondary metadata element, not a headline.
- **D-09:** This requires a new database column on `cards` (something like `numero` or `sequencial`, an integer, unique, auto-assigned). **This is a schema change against production** — the same rigor as Phase 4 applies: additive migration, rehearsal before apply, verification after. Do not casually bolt this onto an application-layer plan; it needs its own migration-first treatment if the planner determines a new column is the only viable approach (it almost certainly is — there's no existing integer identity column to repurpose, `cards.id` is a UUID).

### Vencimento rule — settled, supersedes Phase 5's A-02

- **D-10:** New rule for a parcela's `vencimento` day-of-month: if the contract has `periodo_inicio`, the day is the day-of-month of `periodo_inicio` (same as today — this part is unchanged). If the contract has **no** `periodo_inicio`, the day is now **20** (fixed) — this **replaces** Phase 5's original choice of "last day of the month" (see `05-01-PLAN.md`'s A-02, which chose month-end specifically to avoid contracts without a registered due day showing as immediately overdue; the user has now given an explicit fixed fallback instead, so that reasoning is superseded, not violated).
- **D-11:** The day-capping-to-end-of-month logic (e.g., a contract starting on the 31st capped to Feb 28/29) still applies when `periodo_inicio` exists — only the *no-periodo_inicio* fallback changes, from "last day" to "day 20". Day 20 exists in every month, so no capping is needed for that branch.

### Generation scope — settled, the highest-risk change in this phase

- **D-12:** When a contract has **both** `periodo_inicio` and `periodo_fim`, generation must ensure a parcela exists for **every month** in `[periodo_inicio, periodo_fim]` — not just current + next. Example given by the user: a Jan–Dec 2026 contract generates 12 parcelas.
- **D-13 — retroactive/backfill, explicitly confirmed:** This includes months **before today** that fall within the contract's period. The user was shown the alternative ("só de hoje em diante, mesmo dentro do período") as the recommended, lower-risk option and **explicitly chose full retroactive generation instead** ("Gerar retroativo também"). This reopens and reverses a decision from the original approved spec (`.planning/financeiro-modulo-prompt.md`), which had explicitly excluded historical backfill (see also `REQUIREMENTS.md`'s former `FIN-FUT-03`, now promoted to PARCELA-06). Do not treat this as an oversight to flag back to the user — it is a confirmed, deliberate reversal.
- **D-14:** Contract with `periodo_inicio` **but no** `periodo_fim` (open-ended/indeterminate term — common in Brazilian rental law after an initial fixed term): treated as **not** having a "período completo" — falls back to the Phase 5 behavior (current + next month only). User confirmed explicitly ("Tratar como 'sem período completo'"). Do not attempt to generate a rolling window for this case.
- **D-15:** Contract with neither date: unchanged, current + next month (Phase 5 behavior, PARCELA-01).
- **D-16:** Trigger point for generation is **unchanged** — still lazy, still fires only when the Financeiro route is loaded (no new Server Action on card save/edit, no cron). User explicitly confirmed keeping the existing architecture ("Continuar só ao abrir o Financeiro") over adding a Board-side trigger. This means a contract that already has months backfilled won't re-backfill on every load (idempotency, PARCELA-02, must hold here too) — the existing check-then-insert pattern in `garantirParcelas()` extends naturally to a larger set of target competências, it does not need a different mechanism.
- **D-17 — production blast-radius check required before implementation.** Unlike Phases 4-6, this phase can silently create dozens of "Vencida" parcelas in one page load for contracts with long, already-elapsed periods. A pre-flight SQL query against production (counting how many active contracts have both dates, and the total parcela count a full backfill would create) **must run and be reviewed before the execution plan proceeds past a checkpoint** — same spirit as Phase 4's `checkpoint:decision` before `supabase db push`, adapted to an application-layer change instead of DDL. See `.planning/sketches/preflight-task.md` for the exact queries already prepared (a parallel session may have already run these — check for a result in the conversation/session history before re-deriving).
- **D-18:** `valor_original` for a backfilled (retroactive) parcela uses the **current** `cards.valor` — there is no historical rent-value tracking, so this is the only available approximation (same snapshot mechanism as PARCELA-03, just applied to a past competência). This is a known, accepted limitation — if rent changed mid-contract, backfilled parcelas will reflect the current rate, not the historical one. Correctable via the existing "Ajustar" action (desconto/acréscimo) if the user needs to fix a specific one — matches the project's "correção fácil" pillar, no special-case handling needed in the generation logic itself.

### Claude's Discretion

- Exact shape of the "período" filter field (single month picker vs. date range vs. two separate início/fim fields) — the sketch used `<input type="month">` against `vencimento`; confirm this is still the right target field (vs. `competencia`) at UI-SPEC time.
- Whether ID filtering is exact-match or partial/prefix match.
- Visual placement and treatment of the new sequential ID badge on the Board card (D-08) — must not compete with `valor` as the card's focal point, per Phase 5's UI-SPEC hierarchy rules.
- Exact migration approach for the new `cards` ID column (column name, whether backed by a `sequence`/`serial`/`identity`, or assigned by a one-time backfill UPDATE keyed to existing `created_at` order for the ~46 existing rows) — needs its own design, follow the Phase 4 migration's additive/rehearsed pattern.
- Whether the empty-state copy for "no parcela due today" needs a distinct message from "no results for this filter" (the sketch already implemented both distinctly — reuse that as the default unless a reason to change surfaces).
</decisions>

Como conciliações bancárias, cancelamento de parcelas e gerar relatórios 'pdf e excel'." "Cancelamento de parcelas" is net-new, undesigned — do not build any cancel/delete capability in this phase; it has no data model yet (the ledger is append-only with no cancellation concept) and needs its own dedicated discussion when it comes up.
