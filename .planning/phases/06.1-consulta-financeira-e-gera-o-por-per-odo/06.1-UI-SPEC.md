# Phase 6.1 — UI Design Contract

> Visual and interaction contract for the query/filter layer that replaces the Mês atual/Próximo mês
> switcher in the Financeiro tab, plus the new sequential contract-ID badge (Board card + Financeiro
> consulta). Brownfield spec, extending **two already-approved** UI-SPECs
> (`.planning/phases/05-.../05-UI-SPEC.md`, `.planning/phases/06-.../06-UI-SPEC.md`) and formalizing an
> **already user-approved sketch** (`.claude/skills/sketch-findings-kanban-para-aluguel/`, sketch 001,
> variant B). No new palette, no new font, no new spacing scale is introduced. Where this phase amends
> a Phase 5/6 decision, the amendment is called out explicitly, matching the precedent Phase 6 already
> set when it amended Phase 5.
>
> **Source of truth for the locked interaction/copy decisions below:** CONTEXT.md D-01–D-18 and
> `.claude/skills/sketch-findings-kanban-para-aluguel/references/consulta-e-filtros-financeiro.md`.
> This document formalizes those into exact classes/copy/component choices — it does not re-litigate
> them. The one genuinely open item this document designs from scratch is the Board card ID badge
> (D-08), flagged explicitly below.

**Existing shadcn primitives already installed and reused as-is** (no re-init): `dialog`, `sheet`,
`button`, `input`, `label`, `textarea`, `table`, `alert-dialog`, `separator`.

**One new shadcn primitive is required: `collapsible`.** The sketch's filter drawer used a hand-rolled
`max-height` CSS transition (`overflow:hidden; max-height:0 → 240px`) — explicitly a sketch-only
shortcut per this task's own instructions, not a production pattern. The real implementation must use
`@base-ui/react/collapsible` (already present in `node_modules/@base-ui/react/collapsible`, same
package this project already consumes for `dialog.tsx`/`sheet.tsx`), wrapped in a new
`components/ui/collapsible.tsx` following the **exact structural pattern** `sheet.tsx` already
establishes in this repo (`data-slot` attributes, `cn()`, `data-starting-style`/`data-ending-style`
transition hooks, `"use client"`):

```tsx
"use client"

import * as React from "react"
import { Collapsible as CollapsiblePrimitive } from "@base-ui/react/collapsible"

import { cn } from "@/lib/utils"

function Collapsible({ ...props }: CollapsiblePrimitive.Root.Props) {
  return <CollapsiblePrimitive.Root data-slot="collapsible" {...props} />
}

function CollapsibleTrigger({ ...props }: CollapsiblePrimitive.Trigger.Props) {
  return <CollapsiblePrimitive.Trigger data-slot="collapsible-trigger" {...props} />
}

function CollapsiblePanel({ className, ...props }: CollapsiblePrimitive.Panel.Props) {
  return (
    <CollapsiblePrimitive.Panel
      data-slot="collapsible-panel"
      className={cn(
        "overflow-hidden transition-[height] duration-200 ease-out data-ending-style:h-0 data-starting-style:h-0",
        className
      )}
      {...props}
    />
  )
}

export { Collapsible, CollapsibleTrigger, CollapsiblePanel }
```

If `npx shadcn add collapsible` resolves against the `base-nova` registry and produces an equivalent
file, prefer the CLI output; the hand-authored version above is the fallback contract if the registry
block differs or is unavailable — either way the resulting API (`Collapsible`/`CollapsibleTrigger`/
`CollapsiblePanel`, real height animation via the primitive's own transition hooks, not a manual
`max-height` guess) is what this phase's filter drawer must be built on.

## Interaction Contract

### Filter drawer — a real collapsible primitive, not a CSS trick

The drawer's open/closed state is local component state (`React.useState`, `"use client"`, same
pattern `MesSwitcher` already used) driving `Collapsible`'s `open`/`onOpenChange`. **Initial state on
page load:** open if the current URL already has one or more filter query params (the user is looking
at a filtered result and should see what produced it without an extra click); closed otherwise
(the common case — checking what's due today — starts with the drawer collapsed, per D-05's explicit
"keeps the tab visually calm" reasoning).

### Applying and clearing filters — a real server round-trip, not client-side filtering (amends how Phase 5 read data)

The sketch's own interaction log is explicit that this is a **"consulta", not "busca instantânea"**
(`applyFilter` only runs on the `Consultar` click, never on keystroke). This phase carries that same
discipline into the real data flow, and goes one step further than the sketch's in-memory array: because
a period filter can legitimately target *any* past or future month (PARCELA-06's retroactive
generation can produce parcelas spanning years), the default view's small "vencendo hoje" dataset is
**not** sufficient to filter client-side — a filter submission must be a real query against the server,
not a JS `.filter()` over already-loaded rows.

1. **Consultar:** the client builds a `URLSearchParams` from only the non-empty fields (empty fields are
   omitted entirely, never sent as empty strings — this is what keeps "each filter optional, AND-combined"
   true at the query-string level too) and calls `router.push(`/financeiro?${params}`)`. This is a normal
   Next.js client-side transition (not a full browser reload); `financeiro/page.tsx` re-runs as a Server
   Component reading the new `searchParams` and re-queries Supabase with the filters applied instead of
   the "vencendo hoje" query. The drawer stays open after the navigation (see initial-state rule above).
2. **Limpar:** clears the four local input values **and** calls `router.push("/financeiro")` (no query
   params) — returning to the default "vencendo hoje" view. The drawer does **not** auto-collapse (matches
   the sketch's `clearFilter()`, which never calls its toggle function) — the user is left with an empty,
   ready-to-fill form, not sent back to a closed panel they'd have to reopen.
3. **Loading state:** the route transition inherits `app/(app)/loading.tsx`, the same route-level loading
   UI Phase 5 already established covers Financeiro — no new spinner or skeleton is introduced specifically
   for the filter form, consistent with that precedent.
4. **Exact Supabase query shape** (date-range for the month field, `.ilike()` for the two name fields,
   exact match on `numero`) is a data-layer decision for the plan, not this contract — this section only
   fixes the *observable* behavior: a filter submission always re-renders from the server; it never
   mutates the table in place.

### Selecting a parcela from either view

Unchanged from Phase 6 (D-06): whatever row appears — default or filtered — its `Ações` cell still opens
the same `Pagamento`/`Ajustar`/`Histórico` surfaces, unmodified. This phase only changes the path to a
row, never what happens once you're on it.

## Visual Hierarchy

### Financeiro page — header row (amends Phase 5's ranked list)

Phase 5 ranked the Mês atual/Próximo mês switcher as item 3 in the page's visual weight order ("the only
pill-shaped interactive control above the table"). That control is **removed** (D-01), and this phase's
header row takes its structural place — same position in the layout, same job (the one interactive
element between the page title and the table), different shape and content:

1. **Parcelas table panel** — unchanged, still the only permanently-raised `bg-card` surface holding the
   data
2. **Page title h1** — unchanged
3. **Header row** (replaces the switcher): `{list heading}` + `{subheading}` on the left, `{result count}`
   + `Filtrar`/`Fechar filtros` button on the right — `justify-between`, matching the sketch's layout
   exactly. The heading is `font-heading text-base font-bold` (the same visual weight the switcher's
   active segment used to carry via `shadow-sm`), so the page still reads "here is the one thing above
   the table that tells you what you're looking at"
4. **Filter drawer** (new, collapsed by default) — sits between the header row and the table panel when
   open; contributes zero visual weight when closed (an outline button is all that's visible)
5. **Page subheading** — unchanged position, 14px muted, explanatory only

### Board card — ID pill placement (the one open design decision, resolved here)

**Not covered by the sketch** (D-08 explicitly flags this as Claude's discretion). Reviewed
`card-item.tsx`'s current structure to place it: the card's bottom row (`mt-2 flex items-center
justify-between gap-2`) already holds `valor` (left, `text-sm font-semibold text-primary`, the card's
established focal point per Phase 5) and the ativo/inativo pill (right). This phase adds the ID pill
**into that same right-hand group**, not as a new row and not next to `proprietario` at the top:

```
[ valor (left, unchanged, sole focal point) ]     [ #12 ]  [ Ativo ]
                                                    ↑ new    ↑ unchanged
```

```tsx
<div className="mt-2 flex items-center justify-between gap-2">
  <p className="text-sm font-semibold text-primary">{formatCurrency(card.valor)}</p>
  <div className="flex items-center gap-1.5">
    <span
      className="inline-flex h-5 items-center rounded-full bg-secondary px-2 text-xs font-semibold tabular-nums text-secondary-foreground"
      aria-label={`Contrato número ${card.numero}`}
    >
      #{card.numero}
    </span>
    <button /* existing ativo/inativo pill, unchanged */>...</button>
  </div>
</div>
```

**Why this placement and not the top of the card (next to `proprietario`):** `proprietario` is the
card's second-heaviest text after `valor` (bold, 14px, first line read). Placing a badge next to it — even
a small one — would visually pair the ID with the card's *identity*, competing for the same first-glance
attention `valor` already claims per Phase 5's hierarchy rule. Placing it in the bottom row instead groups
it with the card's **other** secondary-metadata pill (ativo/inativo), a location Phase 5 already
established as "quiet companion information, not headline." Within that pair, the ID pill is
deliberately the quieter of the two: `bg-secondary` (a neutral, unsaturated fill) sits visually behind
the ativo pill's `bg-primary/10` (a tinted-but-still-accent fill) — so even inside the "secondary" group,
`valor` > ativo-pill > id-pill, a clean three-step weight order with no ties.

**Why grouped with ativo/inativo rather than given its own third row:** a third row would either need its
own `mt-2` (pushing total card height up on all ~46 cards at once, a layout-budget cost for a feature
most days nobody looks at) or crowd against the existing two-pill row's baseline. Grouping costs zero
extra vertical space and reuses the exact gap token (`gap-1.5`) already proven at this size on this card.
