# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase creates a new route (`/relatorios/financeiro`) and a new component tree, reusing several already-shipped, reviewed pieces — `StatTile`, `Collapsible`/`CollapsiblePanel`, `Table`/`TableHeader`/`TableRow`/`TableCell`, `formatCurrency`/`formatDate` — verbatim/unmodified, and two more — `FilterChip`, `ParcelaSituacaoBadge` — via one small additive, optional `className` prop each (see Layout & Component Contract §8), needed only to keep this phase's own weight/spacing budget on-grid; every existing call site of both components (Phase 5/6/7/8 screens) passes no such prop and renders pixel-identical to today. This phase also adapts one component's *mechanics* (`FiltroRelatorioFinanceiro`, Phase 8) from click-triggered to live/dynamic per D-01, as new markup, not a shared-file edit. The existing `/relatorios` page (`reports-view.tsx`) otherwise gets exactly one addition: an entry-point button — every other pixel of that page and of `08-UI-SPEC.md`'s contract is untouched. No new design tokens are introduced anywhere in this contract — every value below sits on the standard 8-point spacing scale (4/8/16/24/32/48/64) and within a 2-weight (400/600) typography budget. This contract additionally covers the **exported PDF's** visual layout (RELDED-05) — a print/document medium, specified separately from the on-screen contract below.

## Layout & Component Contract

**Visual hierarchy.** Unlike Phase 8's two-stage hierarchy (filter panel first, then results after a click), this page has a **single, always-populated hierarchy** from first paint: header → actions row → (optional) filter panel → 4-tile summary → list. The 4-tile summary and the list are the payoff and are visible immediately with the full, unfiltered totals (same universe as Phase 8, D-05 — archived/inactive contracts count); the filter panel is available but collapsed, narrowing what's already showing rather than gating it.

**1. Route and data**
New Server Component `web/src/app/(app)/relatorios/financeiro/page.tsx`, structured like `relatorios/page.tsx`: fetches parcelas once server-side (reusing the same query shape as `buscarParcelasRelatorioAction`, or calling it directly — planner's call) plus `hojeEmCuiaba()`, and passes both as props to a new client component (e.g. `web/src/components/reports/relatorio-financeiro-dedicado.tsx`). The client component holds the live filter state (`FiltroRelatorioValores`) and derives categorias + filtered rows via `useMemo` on every field change (Claude's Discretion in `10-CONTEXT.md`: fetch once, filter in memory — confirmed the right call given ~48 contracts/few-hundred parcelas). `calcularRelatorioFinanceiro` is reused verbatim for the 4 tiles; the new row-list needs its own lightweight filter pass reusing the same `passaFiltroTexto`/`passaFiltroPeriodo`/situação-membership logic already exported from `relatorio-financeiro.ts` (D-03 — one row per parcela, not per contract) — do not reimplement that matching logic a second time.

**2. Header**
Back link ("Relatórios") above the `h1`. Then `h1` "Relatório Financeiro" + subtitle, same block shape as `/relatorios`' own header (`reports-view.tsx:134-141`), reusing its exact class strings.

**3. Actions row**
Directly below the header: `<div className="flex flex-wrap items-center justify-between gap-4">` containing, on the left, the live result counter ("{filtradas} de {total} parcelas"), and on the right, `<div className="flex items-center gap-2">` with two buttons side by side: "Filtrar" (`Button variant="outline" size="sm"`, `Filter`/`X` icon swap, toggles the panel below) and "Exportar PDF" (`Button variant="default"`, `FileDown` icon) — Exportar PDF is visually last/rightmost, the terminal action of the row.

**4. Filter panel (new markup, adapted from `FiltroRelatorioFinanceiro`'s pattern — not the same file)**
Closed by default (10-CONTEXT.md "Claude's Discretion"). Same fields, same order, same field-label/placeholder copy as Phase 8's `FiltroRelatorioFinanceiro` (Imóvel → Proprietário → Período → Situação chips). Because this phase must remove the submit button (below), it is authored as its own component rather than an import of `filtro-relatorio-financeiro.tsx` — so its classes are this phase's own on-grid choice, not an inherited value: panel surface `mt-4 rounded-2xl border border-border bg-card px-6 py-4`, field wrapper `flex flex-col gap-2` (Label above Input). Differences from Phase 8's version:
- No "Gerar relatório" button inside the panel — every `onChange` updates local state directly, which the parent's `useMemo` picks up live (D-01). There is nothing to submit.
- "Limpar filtros" remains, ghost button, conditional on non-empty filter, right-aligned inside the panel where the button row used to be.
- Otherwise the same visual object as Phase 8's panel — same field order, same chip row, same border/surface treatment — just on-grid spacing and one fewer button, not a redesign.

**5. Four-category tile grid**
`StatTile` reused unmodified, same `grid gap-4 sm:grid-cols-2 xl:grid-cols-4` as Phase 8, same icon-to-situação mapping (`CheckCircle2`/`Clock`/`AlertCircle`/`Lock`), same `tone="alert"` rule for `vencida` when `quantidade > 0`. Always rendered (no pre-generation placeholder state exists on this page, unlike Phase 8) — recalculated on every keystroke via the shared `useMemo`.

**6. Parcela list (new — does not exist in Phase 8)**
Below the tile grid, wrapped in a `rounded-2xl border border-border bg-card p-6` panel — same card family as `ParcelasTable`'s, at this phase's own on-grid padding (`p-6` rather than that file's `p-5`, since this is new markup, not a reuse of that component). Reuses `Table`/`TableHeader`/`TableRow`/`TableHead`/`TableCell` from `@/components/ui/table`, same as `ParcelasTable`/`ArquivadosView`. Exactly six columns, in this order, per D-03 (no more, no less — no ID column, no Ações column, this list is read-only):

| Column | Cell content | Alignment | Notes |
|--------|-------------|-----------|-------|
| Imóvel | `endereco` | left | `text-sm font-semibold text-foreground`, same weight as `ParcelasTable`'s Imóvel column |
| Proprietário | `proprietario` | left | `text-sm text-muted-foreground` |
| Competência | mês por extenso + ano (e.g. "Agosto de 2026") | left | Reuse the existing `mesFormatter`/`mesPorExtenso` pattern already duplicated across `parcela-historico-sheet.tsx`/`destravar-parcela-dialog.tsx`/`ajustar-parcela-dialog.tsx`/`registrar-pagamento-dialog.tsx` — do not invent a new competência format (e.g. "08/2026") for this one table |
| Vencimento | `formatDate(vencimento)` | left | `tabular-nums text-muted-foreground`, same as `ParcelasTable` |
| Situação | `<ParcelaSituacaoBadge situacao={...} className="gap-2" />` | left | The component's `Situacao` prop type is a superset of `SituacaoRelatorio`'s four values, safe to pass directly. Passes the additive `className` override (§8) so this list renders the badge's icon-to-label gap as `gap-2`, not its internal default `gap-1.5` |
| Valor | `formatCurrency(...)` | right | `text-right tabular-nums`. Value shown follows the same D-07 rule already encoded in `calcularRelatorioFinanceiro`: pagas/conciliadas show `valorPago`, a_vencer/vencidas show the outstanding balance (`valorDevido - valorPago`, floored at 0) — do not show `valor_original` unconditionally, that would silently disagree with the tile totals directly above it |

Sort order: by `vencimento` ascending (chronological) — a defensible, explicit default (not specified in `10-CONTEXT.md`, resolved here): matches the Financeiro tab's own chronological habit and the structural cadence of the Sienge reference the user attached (chronological list, oldest due date first), without inventing per-date subtotal rows that D-04 doesn't call for (see PDF section below for why grouping/subtotals were deliberately not carried over). Apply identically on-screen and in the PDF export, so the two never disagree about ordering.

**7. Data/behavior notes for the planner (not visual, but shape the copy/UI states above)**
- Archived/inactive contracts count toward the tiles and the list (D-05, unchanged from Phase 8) — the query must not silently apply the `arquivado_em is null` filter used by the contract-status report on `/relatorios`.
- Período filter applies to `competencia`, not `vencimento` (D-08 from Phase 8, same semantics reused here for consistency with the Financeiro tab).
- Situação is computed on read via `situacaoDaParcela` against `hojeEmCuiaba()`, never stored or reimplemented.
- The live `useMemo` must be efficient enough not to visibly lag on every keystroke at current scale (~48 contracts, few hundred parcelas) — no debounce needed at this volume, but if the planner finds evidence otherwise, a short debounce (150–250ms) on the two free-text fields only (not the month/chip fields, which change less frequently) is an acceptable implementation detail that does not change this contract's visual output.

**8. Two additive, non-breaking component changes (the only edits this phase makes to already-shipped files)**
Both `FilterChip` (`reports-view.tsx`) and `ParcelaSituacaoBadge` (`parcela-situacao-badge.tsx`) hard-code one off-grid value each internally — `font-medium` (500 weight) and `gap-1.5` (6px) respectively — values this phase cannot declare within its own budget (2 weights / on-grid spacing) without either forking both components or editing them. The fix: give each an **optional `className` prop**, merged last via the project's existing `cn()` utility (`clsx` + `tailwind-merge`, `web/src/lib/utils.ts`) so a passed-in class cleanly overrides the matching default utility (tailwind-merge resolves same-group conflicts in favor of the later class). This phase's own usages pass `className="font-semibold"` (chip, §Typography) and `className="gap-2"` (badge, §6 table); every existing call site of both components (Phase 5/6/7/8 screens) passes no such prop and keeps rendering `font-medium`/`gap-1.5` exactly as shipped today — zero visual change outside this phase's own new page. This is the full extent of this phase's touch on already-shipped files; everything else it needs is new markup in new files.

## PDF Export Layout Contract

Governs RELDED-05's visual output. The **library/rendering approach is a planning-stage technical decision** (10-CONTEXT.md "Claude's Discretion" — client-side print CSS, `jsPDF`/`html2canvas`, or server-side generation, each checked for Next.js 16/React 19/Turbopack compatibility per `web/AGENTS.md`); this section specifies what the resulting document must look like regardless of which approach is chosen.

**Reference used, and how.** The user attached a real export from another system ("Sienge/Starian") as a structural reference, explicitly asking for something "bem estruturado e resumido... em um estilo de lista." Per the reference brief, this project's PDF does **not** copy Sienge's business fields (indexador/juros/multas — not part of this app's data model) or its per-day/per-month cascading subtotal rows (`Total do dia` / `Total do mês` / `Total da empresa` / `Total geral`) — those exist in Sienge because its report has no equivalent of this app's 4-category breakdown. This app's "totals" **are** the 4 categories (D-04, locked) — they map directly onto the *shape* of Sienge's own end-of-report summary-stats block (`Vencido no período` / `A vencer no período` / `Total de parcelas` / `Valor médio`, page 2 of the reference), not onto its per-day subtotals. What **is** carried over, deliberately: (a) a compact, bordered, label:value header table for the applied filters (mirrors Sienge's "Empresa / Período / indexador / juros" header block), (b) a clean, single flat tabular list with no visual clutter, and (c) a totals/summary block positioned at the end. This is the "grouped list with subtotals, clean tabular hierarchy, compact label:value header blocks" visual language the reference was chosen for — adapted, not copied, to this app's simpler 4-total shape per D-04.

**1. Page format**
A4, portrait. Six columns (Imóvel/Proprietário/Competência/Vencimento/Situação/Valor) fit comfortably in portrait at the type sizes below — no landscape needed (unlike the reference, which carries ~13 columns of Sienge-specific fields this app doesn't have).

**2. Header block (top of page 1 only)**
- Document title: "Relatório Financeiro" — same weight/prominence as an `h1`, roughly 18–20pt bold, `--foreground` `#18341c` (or the PDF-safe equivalent if the rendering path can't consume CSS custom properties — always fall back to the literal hex from `globals.css`, never invent a new color for print).
- Generation timestamp, right-aligned on the same line or directly beneath: "Gerado em {data} às {hora}" (Cuiabá time, via `formatInstantDate`/`hojeEmCuiaba` — never a raw UTC timestamp, same rule as the rest of the app).
- Applied-filters block: a bordered, compact label:value table (mirrors Sienge's header table structurally), one row per active filter dimension — Imóvel, Proprietário, Período, Situação — each showing the value that was active at export time, or "Todos"/"Todas" when that dimension wasn't filtered. This is what makes the PDF self-explanatory per D-04 ("ninguém que abrir o PDF depois precisa lembrar ou adivinhar o que foi filtrado") — never omit a row, even an unfiltered one, so the reader can tell "not filtered" apart from "filter value not captured."

**3. Summary/totals block**
Positioned directly below the header block, above the list. Four label:value pairs, one per category (Pagas / A vencer / Vencidas / Conciliadas), each showing count + money total — the PDF-native rendering of the same `CategoriaRelatorio[]` the on-screen `StatTile` row shows, laid out as a compact bordered row/table (Sienge summary-stats shape), not as four separate boxed cards (print doesn't need the screen's card affordance — a denser tabular block reads better on paper and matches "resumido").

**4. List**
A single flat table, same six columns and same sort order (vencimento ascending) as the on-screen list in §6 above — no per-date or per-month subtotal grouping rows (deliberately not carried over from the reference, see note above; D-04 asks for "a lista completa," not a grouped ledger). Header row repeats on every page if the list spans multiple pages (standard print-table behavior — any chosen library/CSS approach must support this, it is not optional at scale: production already has ~350+ parcelas across all contracts, an ungrouped list without repeating headers on a filtered-down PDF spanning 2+ pages would be unusable). Row density: tighter than the on-screen table (paper has no hover/click affordance to protect) — roughly 9–10pt body text, alternating row shading optional but not required (`--muted` `#eaf6e6` on every other row is acceptable if the chosen rendering path supports it cheaply; a plain white list with just border-bottom rules per row is an acceptable, simpler fallback — do not block implementation on alternating shading).

**5. Empty result in PDF**
If the filtered list has zero rows at export time, the PDF still generates (D-04 does not say to block export on empty results) — header block and summary block render normally (all four totals legitimately show 0/R$ 0,00), and the list area shows the same copy as the on-screen empty state: "Nenhuma parcela encontrada para os filtros aplicados." Never silently produce a PDF with a blank list area and no explanation.

**6. Footer (every page)**
Small, muted text: page number ("Página X de Y") and a short system attribution line ("Kanban Aluguel — gerado em {data}") — mirrors the reference's footer convention (timestamp + system name) at a much lower visual weight than the reference's, since this isn't a paid third-party product needing its own branding weight, just a lightweight provenance line.

**7. Typography (PDF-specific — a print medium, sized in pt, separate from the on-screen `px` scale above)**
| Role | Size | Weight |
|------|------|--------|
| Document title | 18–20pt | Semibold |
| Section label (header table labels, summary block labels) | 8–9pt, uppercase | Semibold |
| Header/summary values | 9–10pt | Regular |
| Table header row | 9pt, uppercase | Semibold |
| Table body | 9–10pt | Regular |
| Footer | 7–8pt | Regular |

Exactly two weights — 400 regular / 600 semibold — the identical budget as the on-screen contract above, not a separate scale. Do not introduce Bold (700/800) anywhere in the PDF.

**8. Color (PDF-specific — hex fallbacks, for rendering paths that can't consume CSS custom properties)**

| Text / foreground | `#18341c` |
| Muted text (labels, footer) | `#5c7060` |
| Borders / rules | `#dbeed4` |
