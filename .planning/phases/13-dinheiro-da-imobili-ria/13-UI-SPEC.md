# Phase 13 — UI Design Contract

> Visual and interaction contract for Dinheiro da imobiliária. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

Unlike Phases 11/12 (one small, well-precedented surface each), this phase introduces **four
distinct new surfaces**, two of which have no direct analog in the codebase. This document covers
all four. No shadcn component is newly installed — every primitive used below (`Dialog`, `Sheet`
+ `SheetFooter`, `Table`, `Input`, `Label`, `Textarea`, `Button`, `StatTile`) is already present
under `web/src/components/ui/` or `web/src/components/reports/`, reused verbatim. No new design
token (color/spacing/typography) is introduced — every value sits on the same 8-point spacing
scale and 2-weight (400/600) typography budget already established by `10-UI-SPEC.md`/
`12-UI-SPEC.md`, with one explicit, named exception carried over unchanged from the existing
dialog family (see Spacing Scale).

**The four surfaces, and where each is specified:**

| # | Surface | Requirement | Route / Location | Spec section |
|---|---------|-------------|-------------------|---------------|
| 1 | Configuração financeira (percentuais por contrato) | IMOB-01 | New route `/financeiro/configuracao` | Layout & Component Contract §1 |
| 2 | Campo de taxa no diálogo de pagamento | IMOB-02, IMOB-03 | Extends `registrar-pagamento-dialog.tsx` (existing) | Layout & Component Contract §2 |
| 3 | Ciclo de vida da caução | IMOB-04 | Lives inside surface #1 (Configuração financeira), not the Board or the Financeiro table | Layout & Component Contract §3 |
| 4 | Relatório de reconciliação ("Dinheiro da imobiliária") | IMOB-05 | New route `/relatorios/imobiliaria` | Layout & Component Contract §4 |

**Deliberate placement call for Caução (13-CONTEXT.md left this to UI-SPEC discretion):** the
Caução action lives *only* inside the new Configuração financeira screen (surface #1), reached via
an "Caução" button per contract row — **not** on the Board card face, and **not** as a new column
in the existing Financeiro table. Reasoning: (a) `card-item.tsx` is already visually dense
(proprietário, endereço, inquilino, valor, `IdPill`, archive/delete icon buttons) — a fifth
low-frequency action there would compete for space with controls used every day; (b) the existing
Financeiro table (`ParcelasTable`) is per-*parcela*, not per-*contrato* — caução is a contract-level
concept with no natural row to attach to without duplicating it across every parcela of a contract;
(c) Configuração financeira is already the "per-contract financial settings" home (percentuais live
there per D-02), so bundling caução there keeps one mental model instead of three. This keeps every
pixel of the Board and the existing Financeiro table (`FinanceiroView`/`ParcelasTable`) completely
untouched — a stronger guarantee than D-04 strictly required (D-04 only locked Financeiro/
Relatórios/Relatório Financeiro dedicado), extended here to the Board for the same "estritamente
aditiva" spirit stated in 13-CONTEXT.md's `<domain>`.

**Entry points, not new nav items.** Following the precedent set by RELDED-01 (`10-UI-SPEC.md`,
"Relatório financeiro" reached via a button inside the existing `/relatorios` page, not a new
top-level sidebar item), both new routes are reached via a button placed inside an existing page,
never added to `AppShell`'s `NAV_ITEMS`. Both are low-frequency screens (setup-once and
period-end-checking, respectively) — adding two more entries to a sidebar that already lists
Board/Financeiro/Relatórios/Arquivados would dilute the four screens people open daily.

Declared values (must be multiples of 4):

| Token | Value | Usage |

| lg | 24px | `p-6` — page container, Configuração financeira table card, reconciliation list card (matches `RelatorioFinanceiroLista`'s `p-6`, not `ParcelasTable`'s `p-5`, because both new tables are full-page-level surfaces like the Phase 10 list, not a nested Financeiro panel) |
| xl | 32px | Not used this phase |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

**Exception (named, carried over unchanged — not a new decision):** `gap-1.5` (6px) for
label-above-input field stacks inside every new/extended dialog (`RegistrarPagamentoDialog`'s new
taxa field, `ConfigurarPercentuaisDialog`, `RegistrarEventoCaucaoDialog`). This is not introduced
by this phase — `registrar-pagamento-dialog.tsx` and `ajustar-parcela-dialog.tsx` already use
`flex flex-col gap-1.5` for every field in those exact dialogs today. The new taxa field lives
*inside* `RegistrarPagamentoDialog`, next to three fields already on 6px rhythm — using `gap-2` for
only the new field would create visible inconsistency *within a single dialog*, a worse outcome
than the existing off-grid value. The two brand-new dialogs (`ConfigurarPercentuaisDialog`,
`RegistrarEventoCaucaoDialog`) copy the same `gap-1.5` for cross-dialog consistency across the
whole Financeiro dialog family (`RegistrarPagamentoDialog`/`AjustarParcelaDialog`/
`DestravarParcelaDialog`/the two new ones) — one shared exception, not four independent ones.

## Typography

This phase's own new copy uses exactly **two weights**: 400 (regular — body text, values,
observação) and 600 (semibold — headings, table primary cells, tile labels, badges). No third
weight is authored by this phase.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 (Tailwind default) |
| Label / field label | 14px (`text-sm`, shadcn `Label` default `font-medium` 500) | 500 medium (inherited component default, not authored) | `leading-none` |
| Table primary cell (Imóvel column) | 14px (`text-sm`) | 600 semibold (`font-semibold`) | 1.5 |
| Heading (page `h1`) | 24px (`text-2xl`), `font-heading` | 600 semibold (`font-semibold`) | 1.2 — matches `/relatorios/financeiro`'s exact `h1` class string |
| Dialog/Sheet title | 16px (`text-base`), `font-heading` | 500 medium (inherited `DialogTitle`/`SheetTitle` default) | `leading-none` |
| Badge/tile label | 12–14px (`text-xs`/`text-sm`) | 600 semibold | 1.4 |

**Note on reused, unmodified components:** `StatTile` (reused verbatim in the reconciliation
report) renders its number at `font-extrabold` (800) internally — a pre-existing default, not a
new weight introduced by this phase, consistent with how `10-UI-SPEC.md` treated the same
component. `Label` renders at `font-medium` (500) — also a pre-existing shadcn default, inherited
unchanged. Neither counts against this phase's 2-weight authored budget.

## Layout & Component Contract

### §1 — Configuração financeira (`/financeiro/configuracao`)

New Server Component route, structured like `/relatorios/financeiro/page.tsx`: fetch all contracts
(no visibility filter — see note below) server-side, pass to a new client component
`web/src/components/financeiro/configuracao-financeira-view.tsx`.

**Scope divergence from the Financeiro tab's visibility rule, stated explicitly:** this table
shows **every** contract — active, inactive, and archived — unlike `ParcelasTable`'s
`avaliarVisibilidadeParcela` rule (Phase 6.2). Percentuais and caução are contract-level
configuration, not time-scoped parcela data; a contract that went inactive or was archived after
receiving a caução still needs that caução tracked and eventually resolved. Sort: by `numero`
ascending, same convention as the Board.

Table (reuses `Table`/`TableHeader`/`TableRow`/`TableHead`/`TableCell`), wrapped in
`rounded-2xl border border-border bg-card p-6`:

| Column | Cell content | Notes |
|--------|-------------|-------|
| ID | `<IdPill numero={...} />` | Same component, default variant |
| Imóvel | `endereco` | `text-sm font-semibold text-foreground` |
| Proprietário | `proprietario` | `text-sm text-muted-foreground` |
| Administração | `{percentual}%` | `tabular-nums`, right-aligned |
| Comissão 1º aluguel | `{percentual}%` | `tabular-nums`, right-aligned |
| Caução | Status tone (icon + label, see Color §Status tones) | Never color alone |
| Ações | "Editar percentuais" (ghost) + "Caução" (outline) | Two buttons, same row, same pattern as `AcoesCell` in `ParcelasTable` |

Empty state (no contracts at all — edge case, board always has contracts in production but the
component must not crash on zero): "Nenhum contrato cadastrado ainda." — same phrasing family as
every other empty-list message in this codebase.

`ConfigurarPercentuaisDialog`: `Dialog` + `DialogContent className="sm:max-w-md"`, identical shape
to `AjustarParcelaDialog` (title, two labeled fields, helper paragraph, error line, `DialogFooter`
with one submit button) — see Copywriting Contract for exact copy.

### §2 — Taxa field in `RegistrarPagamentoDialog` (existing dialog, extended)

**Parent must pass three new props** to `RegistrarPagamentoDialog`: `percentualAplicavel: number`
(resolved server-side per D-01/D-08 — 50 if this parcela's `competencia` is the `min(competencia)`
for its `card_id`, else the contract's administração percentual) and `origemPercentual:
"administracao" | "comissao_primeiro_aluguel"` (drives the helper-text label — see Copywriting
Contract), computed once by the parent (`AcoesCell`/`ParcelasTable`) the same way `valorDevido`/
`valorPago` already are today — no new client-side lookup inside the dialog itself.

**Live-suggestion interaction (new interaction pattern for this codebase, specified precisely
since no direct precedent exists):**
- On open, the taxa field initializes to `round2(percentualAplicavel / 100 * parsedValorInicial)`
  — the same base amount `valorInicial()` already computes for the "Valor recebido" field.
- While the user edits **"Valor recebido"**, the taxa field recalculates live to
  `percentualAplicavel / 100 * valorAtual` — **unless** the user has already typed directly into
  the taxa field this session (tracked via a local `taxaTocada` boolean, reset on each dialog
  reopen exactly like every other field, per the existing `wasOpen` resync pattern already used in
  this file). Once `taxaTocada` is true, editing "Valor recebido" no longer overwrites the taxa
  field — the user's manual value is never silently clobbered.
- This mirrors a "smart default, sticky once touched" pattern already implicit in how this dialog
  treats `valor` itself relative to `valorDevido`/`valorPago` (computed once via `valorInicial()`,
  then fully free-typed) — same spirit, made explicit here because the taxa field additionally
  reacts to a *second* field's changes, which nothing else in this codebase's dialogs currently
  does.

Field renders exactly like the three existing fields (`flex flex-col gap-1.5`, `Label` above
`Input`), with a `text-xs text-muted-foreground` helper line directly beneath (see Copywriting
Contract for the exact sentence).

**Nothing else in this dialog changes.** Title stays "Registrar pagamento", the two existing
context lines (competência, valor devido/pago) stay verbatim, "Data do pagamento" and "Observação
(opcional)" keep their current position (now third and fourth field instead of second and third),
the submit button stays "Registrar pagamento"/"Registrando...". `AjustarParcelaDialog` is
**explicitly untouched** — per D-07 (13-CONTEXT.md), taxas de gestão stay out of scope and continue
through the existing "Ajustar" (acréscimo) flow with a free-text observação; no taxa field is added
there, and the planner/executor must not infer symmetry between the two dialogs from this section.

### §3 — Caução (`CaucaoHistoricoSheet`, reached from §1's "Caução" button)

Same visual shape as `ParcelaHistoricoSheet` — `Sheet side="right"`, `SheetContent className="w-full p-0 sm:max-w-md"`, `SheetHeader className="border-b border-border"` — with one addition this
codebase's `Sheet` component already supports but no existing call site uses yet: `SheetFooter`
(`mt-auto flex flex-col gap-2 p-4`), reused verbatim for the action button(s).

Body: `<ul className="flex flex-col gap-3">` inside `<div className="flex-1 overflow-y-auto p-4">`
— same list-of-cards shape as `ParcelaHistoricoSheet`'s `<li className="flex flex-col gap-2
rounded-xl border border-border bg-card p-3">`. Order: chronological ascending (oldest first),
same convention as `LancamentoDetalhado[]` already renders in `ParcelaHistoricoSheet` — do not
introduce reverse-chronological ordering here just because the reconciliation report (§4) uses it;
the two surfaces serve different purposes (this one is a per-contract audit trail read top-to-
bottom as a story, that one is a period-scoped worklist read newest-first).

Each event card (new `CaucaoEventoLabel` component, mirrors `LancamentoTipoLabel`'s icon+label
shape): icon+label per the status tone table (Color §Status tones — reusing "recebida"/
"devolvida"/"usada" wording per event, not the aggregate contract-status wording used in §1's
table cell), value with sign prefix (`+` recebido, `−` devolvido/usado — same `prefixoValor`
convention as `parcela-historico-sheet.tsx`), date, quem (author), observação if present. No
per-event "Cancelar" action — caução events are append-only with no cancellation mechanism in
this phase's scope (13-CONTEXT.md does not request one; unlike `parcela_lancamentos`, this history
was never exposed for cancellation, so there is no existing pattern to extend and no requirement
asking for it).

`SheetFooter` renders 0/1/2 buttons depending on the computed saldo (received − devolvido − usado,
summed from the event list) — see Copywriting Contract for exact copy and conditions. This is the
only Sheet in this codebase with a persistent action footer; specified explicitly because it is a
new shape, not a reuse.

`RegistrarEventoCaucaoDialog`: `Dialog` + `DialogContent className="sm:max-w-md"`, same shape as
`RegistrarPagamentoDialog` (three fields, error line, one-button `DialogFooter`), `tipo`-aware per
the Copywriting Contract.

### §4 — Reconciliação ("Dinheiro da imobiliária", `/relatorios/imobiliaria`)

New Server Component route, same structure as `/relatorios/financeiro/page.tsx`: server-fetches
the period's events, passes to a client component holding live filter state (same D-01 live-filter
pattern as `RelatorioFinanceiroDedicado`, reused deliberately for UI consistency across this
project's two "relatório" routes — no "Gerar"/submit step, every `onChange` recalculates
immediately).

**1. Header:** back link + `h1` "Dinheiro da imobiliária" + subtitle (Copywriting Contract).

**2. Actions/filter row:** `<div className="flex flex-wrap items-center justify-between gap-4">`
— left: nothing (no live counter needed, six tiles already summarize); right: the "Período" month
input, inline, always visible (no collapsible panel — a single field does not warrant the
Filtrar/Fechar filtros toggle pattern used by the other two report screens, which each have 3+
fields).

**3. Six-tile grid:** `grid gap-4 sm:grid-cols-2 lg:grid-cols-3`, `StatTile` reused verbatim
(unmodified — same component as Phase 8/10). Order: Administração → Comissão 1º aluguel → Total
recebido no período → Caução recebida → Caução devolvida → Caução usada. "Total recebido no
período" = administração + comissão + caução recebida (the three cash-inflow categories — what
actually lands in the bank account); **caução devolvida and caução usada are deliberately excluded
from this sum** (devolvida is a cash *outflow*, usada is not a bank movement at all — see the tile
hint in Copywriting Contract). This is a scoped, defensible v1 total, not an attempt at a
comprehensive net P&L — 13-CONTEXT.md's own `<deferred>` section already signals the user expects
to revise this report's shape after seeing it in use, so this phase deliberately does not invent a
more elaborate combined formula the user hasn't asked for.

**4. List:** below the tiles, `rounded-2xl border border-border bg-card p-6`, `Table` with columns
Data / Contrato / Tipo / Valor / Observação (Copywriting Contract). Sort: **descending** by data
(most recent first) — a deliberate divergence from `10-UI-SPEC.md`'s ascending convention, reasoned
explicitly: that report's use case is "browse the full filtered set," this one's is "I just got a
bank statement, check today's/this week's entries first" — newest-first minimizes scrolling for
the common case. "Tipo" column renders the same `CaucaoEventoLabel`/administração-comissão badge
language as §1/§3, for one consistent vocabulary across every surface in this phase.

**5. No PDF export.** IMOB-05 asks for "um relatório/área," not an exportable document, and
