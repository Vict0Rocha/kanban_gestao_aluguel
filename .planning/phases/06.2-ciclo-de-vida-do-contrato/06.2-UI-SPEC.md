Primitive-choice rules for this phase:

| Surface | Primitive | Why |
|---|---|---|
| Archive confirmation | `alert-dialog` | A confirmation with exactly two outcomes and no free-form data entry — the archetype `AlertDialog` exists for, and the pattern `card-item.tsx` already uses for delete today |
| Delete confirmation (typed) | `alert-dialog` | Still a confirmation, not a form: it collects one throwaway confirmation token, never persisted data. Base UI's `AlertDialog` also does not dismiss on outside click, which is the correct behavior for an irreversible action. It carries an `Input` in its body — permitted, and the reason for the JSX-tree warning below |
| Arquivados list | `table` inside the existing panel shell | Structurally identical to `contracts-table.tsx` (`rounded-2xl border border-border bg-card p-5` + `Table`) — the closest existing analog, per the orchestrator's own pointer |

### ⚠ Load-bearing structural warning — dialogs must be JSX siblings of the sortable div

`card-item.tsx` carries an existing comment explaining that `AlertDialogContent` and `CardDetailDialog`
are **siblings** of the sortable `div`, never descendants: React bubbles synthetic events through the
**JSX tree**, not the portaled DOM position, so a dialog nested inside the sortable div leaks every
keystroke and click into dnd-kit's drag listeners. That already broke typing spaces and selecting text
in the detail form once.

This phase makes that constraint **more** load-bearing, not less: the delete dialog now contains a
text `Input` the user must type `excluir <N>` into. If it is nested inside the sortable div, the space
bar and arrow keys will be swallowed by dnd-kit and the confirmation will be untypeable. Both new
dialogs (`ArquivarContratoDialog`, `ExcluirContratoDialog`) **must** be rendered as siblings of the
sortable div, exactly like `CardDetailDialog` already is.

Consequence: the delete trigger stops being an `AlertDialogTrigger` wrapping the whole card and becomes
a **controlled** dialog (`open` / `onOpenChange` state in `CardItem`), because both new dialogs need
async states (verifying, submitting, blocked). The card's outer `<AlertDialog>` wrapper is replaced by
a fragment.

- **The card's archive button** — `variant="ghost"`, `text-muted-foreground` at rest,

- **The pendency warning** — `text-status-warning` + `TriangleAlert` icon, never a filled banner. A

## Interaction Contract

### Board card — where the archive button goes (D-11) **[JUDGMENT CALL]**

D-11 is literal: bottom-left corner of the card. The bottom-left is currently occupied by `valor`
(`text-sm font-semibold text-primary`), which Phase 5 named the card's sole focal point and Phase 6.1
re-confirmed when it placed the ID pill on the right specifically to stay quieter than it. Two things
cannot occupy one corner, so this contract resolves the collision rather than pretending it away.

**Resolution: an inline leading slot in the existing bottom row, space permanently reserved,
visibility revealed on hover/focus.**

```tsx
<div className="mt-2 flex items-center justify-between gap-2">
  <div className="flex items-center gap-1.5">
    <Button
      variant="ghost"
      size="icon-xs"
      className="-ml-1 text-muted-foreground opacity-0 transition-opacity group-hover:opacity-100 focus-visible:opacity-100 hover:bg-muted hover:text-foreground"
      aria-label={`Arquivar ${card.endereco}`}
      onPointerDown={(event) => event.stopPropagation()}
      onMouseDown={(event) => event.stopPropagation()}
      onClick={(event) => {
        event.stopPropagation()
        setArquivarOpen(true)
      }}
    >
      <Archive className="size-3" />
    </Button>
    <p className="text-sm font-semibold text-primary">{formatCurrency(card.valor)}</p>
  </div>
  <IdPill numero={card.numero} variant="subtle" />
</div>
```

Contract points, each load-bearing:

1. **`opacity-0` + `group-hover:opacity-100`, not `hidden`.** Opacity does not affect layout, so the
   row never reflows on hover. `hidden`→`inline-flex` would jump `valor` sideways ~26px every time the
   pointer crosses the card — jitter across ~48 cards.
2. **`focus-visible:opacity-100` is mandatory.** A control that is invisible but focusable is a
   keyboard trap for sighted keyboard users. *Observation, not a task:* the existing `Trash2` button
   has the same gap and no `focus-visible:opacity-100`. Fixing it is a one-class a11y fix, but it
   touches a Phase 5 surface — flagged here, **not required by this phase**.
3. **All three of `onPointerDown`, `onMouseDown`, `onClick` must call `stopPropagation()`.** The card
   root carries dnd-kit's drag listeners *and* an `onClick` that opens the detail dialog. This is
   exactly the trio the existing `Trash2` trigger already uses — copy it, do not simplify it.
4. **The cost, stated openly:** `valor` sits ~26px in from the card's left text rail instead of flush
   with `proprietario`/`endereco`. Accepted because `valor`'s prominence comes from color and weight,
   not x-position, and because the row now reads as the card's control row. Below is what was
   considered and rejected.

| Rejected alternative | Why |
|---|---|
| `absolute bottom-1.5 left-1.5`, mirroring the delete button | The bottom row's content occupies exactly that box; the button would sit on top of `formatCurrency(card.valor)` |
| `pl-6` on the bottom row + absolute button | Identical indentation cost, plus an absolutely-positioned control whose collision safety depends on a padding value elsewhere in the file |
| Move `valor` to the right, next to the ID pill | Contradicts Phase 6.1's explicit hierarchy ("valor left, unchanged, sole focal point") and pairs the focal point with the quiet metadata. Hard constraint: do not contradict 6.1 |
| Put the archive action in the detail dialog's `Situação` row instead | Contradicts D-11's literal wording. The Ativo/Inativo toggle moved there; archiving did not |
| Always-visible archive button | Puts a low-frequency, irreversible-feeling control permanently adjacent to the card's focal point, on every card. Hover-reveal is this card's established language for card-level actions |

### Archive flow

1. Click the card's archive button → the archive `AlertDialog` opens (card click-through prevented by
   the `stopPropagation` trio).
2. On open, the dialog resolves the open-parcelas count and total. **Three states are required by this
   contract; how the number is obtained (preloaded with the board vs. fetched on open) is the plan's
   call:** `Conferindo parcelas em aberto...` → the `N > 0` or `N === 0` line → or the count-failure
   line. **A failed count never disables `Arquivar`** (D-10: warns, does not block).
3. `Arquivar` **awaits** the Server Action. It does not use `board.tsx`'s optimistic
   `persistOrRevert`. See the deviation note below.
4. On success: the dialog closes and the card is removed from the board's local state.
5. On failure: the dialog stays open, the confirm button re-enables, and the server's message renders
   inline in `text-sm text-destructive`.

### Delete flow

1. Click `Trash2` (top-right, unchanged position and unchanged reveal-on-hover) → the delete
   `AlertDialog` opens **controlled**.
2. On open it checks whether the contract has any lançamento, showing
   `Conferindo o histórico financeiro...` while it resolves. **[JUDGMENT CALL]** This pre-flight is
   deliberate: making a user type `excluir 12` and *then* refusing is the "beco sem saída" feeling
   D-16 exists to prevent. Checking lazily on dialog open — rather than joining lançamentos into the
   board's page query — keeps the board's load cost at exactly what it is today for a control most
   days nobody opens.
3. Resolves to the **allowed** variant (typed form) or the **blocked** variant. If the check itself
   fails, the allowed variant renders with the muted "will still be verified on the server" note —
   the server is the real gate (D-15), so a failed pre-flight must never hard-block a legitimate
   deletion.
4. **Typed confirmation matching:** compare `input.trim().toLowerCase().replace(/\s+/g, " ")` against
   `` `excluir ${numero}` ``. Forgiving about case and stray whitespace (mobile keyboards
   auto-capitalize the first letter), strict about the number — the number is the whole point of the
   ceremony. The input carries `autoComplete="off"`, `autoCapitalize="none"`, `spellCheck={false}`.
5. `Excluir definitivamente` **awaits** the Server Action. On `ok: false` with the movimentação block,
   the dialog **switches to the blocked variant in place** (it does not close, and it does not show a
   toast) — that is the race-condition path, and the user still lands on the archive offer.
6. On success: the dialog closes and the card is removed from the board's local state.
7. The blocked variant's `Arquivar` closes the delete dialog and opens the archive confirmation dialog
   for the same card. **[JUDGMENT CALL]** Two sequential dialogs rather than archiving straight from
   the blocked dialog, because D-10 requires the open-parcelas warning before every archive — and a
   contract blocked for having lançamentos is *precisely* the one most likely to have open parcelas
   worth seeing. Rejected alternative: swapping the blocked dialog's own content into the archive
   confirmation — fewer overlays, but it fuses two independently-triggered surfaces into one
   three-state component for no user-visible gain.

### Deviation from `persistOrRevert`, scoped and justified

`board.tsx` writes optimistically: apply on screen, persist after, revert + `WriteErrorToast` on
failure. `handleDeleteCard` and `handleToggleAtivo` both do this today.

**Archive and delete must not.** Both are confirmed inside a dialog that already owns a natural
pending state (`Arquivando...` / `Excluindo...`, button disabled), so optimism buys no perceived
speed. And optimism is actively wrong for delete: a card that vanishes and then flies back in with a
toast reads as a glitch, when what actually happened is a deliberate, correct policy refusal that
needs to be *read*, not flashed. The refusal message belongs in the dialog the user is looking at.

`handleToggleAtivo` and drag-and-drop keep `persistOrRevert` unchanged. `WriteErrorToast` is untouched
and is **not** used by any surface in this phase.

### Unarchive flow **[JUDGMENT CALL] — no confirmation dialog**

One click on `Desarquivar`, awaited, then `router.refresh()`; the row disappearing from the list is the
confirmation. No `AlertDialog`.

Reasoning: unarchiving destroys nothing, creates nothing, and is undone by the archive button that is
two clicks away on the restored card. A confirmation here would be pure dialog fatigue and would
cheapen the two confirmations in this phase that *are* load-bearing. Nothing regenerates on unarchive
either (D-12: hidden parcelas simply reappear under D-01), so there is no hidden side effect to warn
about.

While the action is in flight the button shows `Desarquivando...` and is `disabled`; on failure an
inline `role="alert"` line appears above the table and the row stays.

### `arquivado_em` date rendering

`arquivado_em` is `timestamptz`. **Never** pass it to `new Date(...)` directly and never pass the raw
value to `formatDate` — this repo has a standing rule (documented in `report.ts`/`parcelas.ts` and
respected by `format.ts`) that ISO date strings parsed by the `Date` constructor shift a day in
Brazil. Slice to `YYYY-MM-DD` first, then `formatDate(...)`. Render date only, no time: the archive
timestamp answers "when did this leave the operation", not "at what minute".

### Nav entry (D-12)

Appended to `NAV_ITEMS` in `web/src/components/app-shell.tsx`, **after** `Relatórios`:

```tsx
{ href: "/arquivados", label: "Arquivados", icon: Archive },
```

No change to `NavLinks`' markup or styling. The active state uses the existing
`bg-sidebar-primary text-sidebar-primary-foreground` treatment — accent rule #1 applying to a new
link, not a new accent use. It inherits the collapsed-rail `title` tooltip and the mobile drawer for
free.

### [JUDGMENT CALL] Silence in the Financeiro — when a hidden parcela needs explaining

The orchestrator asked for this call explicitly. The call is: **silence is correct almost everywhere,
and wrong in exactly one place.**

**Silence is correct for the default "Vencendo hoje" view.** It answers "what is due today". A parcela
hidden by D-01 was never going to be in that answer, and nobody is counting rows against an
expectation. Annotating it would put an explanation of an absence into the one view Phase 6.1
deliberately kept calm.

**Silence is correct for the proprietário / inquilino / período filters.** These are open-ended
searches over the portfolio. A result set that is "smaller than it might have been" has no anchor the
user could compare it against, so there is nothing to reconcile and no confusion to resolve.

**Silence is wrong when the user filters by contract ID.** That filter names *one* contract. The user
has a mental model of it, arrives with an expectation ("this contract has parcelas through December"),
and gets fewer rows — or, if it is archived, zero rows with no hint that the contract even exists.
That is precisely the failure mode that produced this phase: Phase 6/6.1 shipped, `ativo` silently did
almost nothing, and the surprise was only caught by a human staring at production. Shipping a *new*
silent hiding rule into the same screen without a word would be repeating that mistake with better
mechanics.

**Contract:**

- In the ID-filtered view only, when the queried `numero` resolves to a real card that is `inativo` or
  `arquivado`, render one muted explanatory line. Copy is in the Copywriting Contract above.
- **One line, one place, never duplicated.** If the result list is **empty**, the note *is* the
  table panel's message (it replaces the generic `Nenhuma parcela encontrada...`, which would be true
  but useless there). If the list has **rows**, the note renders as a muted `<p>` between the filter
  header and the table panel. Same string either way; only its position moves.
- If the contract is active and unarchived, or no card with that number exists: **no note**, and the
  Phase 6.1 empty state is unchanged, verbatim.
- If resolving the contract fails for any reason, the note is simply absent and behavior is identical
  to today. The note is never allowed to become a failure point in the Financeiro's load path.

This is an **extension** of Phase 6.1's surface, not a restyle: the filter panel, the "Vencendo hoje"
default, the four filters in AND, the Ações column, and the parcela dialogs are all untouched.

### Card detail dialog

**Unchanged.** The `Situação` row (Ativo/Inativo toggle + `IdPill variant="subtle"`) that was moved
there on 2026-08-19 stays exactly as it is. No archive control there, no archived state shown —
archived cards are not on the board, so a board card's detail dialog can never be showing one.

## Visual Hierarchy

### Board card (amends nothing; adds one slot)

Weight order after this phase, top to bottom:

1. `proprietario` — 14px/600 `text-foreground`, first line read
2. `valor` — 14px/600 `text-primary`, the card's sole accent and focal point (**unchanged**)
3. `endereco` / `inquilino` — 12px muted
4. `IdPill variant="subtle"` — `bg-muted` 12px/500, quiet companion (**unchanged**)
5. **Archive button (new)** — invisible at rest, `text-muted-foreground` on reveal. Deliberately the
   lowest-weight element on the card: at rest it contributes exactly zero visual weight, which is the
   only way to add a control to a 48-instance card without raising its overall density
6. Delete button — invisible at rest, `text-muted-foreground` → `text-destructive` on hover
   (**unchanged**)

The two hover-revealed controls sit in opposite corners — destroy top-right, archive bottom-left — a
readable spatial split rather than two adjacent icons the user has to aim between.

### Arquivados page (new — structurally a sibling of Relatórios)

```
h1 "Arquivados"  (font-heading text-2xl font-extrabold)
p  subheading    (text-sm text-muted-foreground)
┌─ panel: rounded-2xl border border-border bg-card p-5 ────────────┐

└──────────────────────────────────────────────────────────────────┘
```

Outer container: `flex flex-col gap-5 p-6`, identical to `reports-view.tsx`. One panel only — no stat
tiles, no chart, no filters. **[JUDGMENT CALL]** Archived contracts are a low-traffic parking lot, not
an analysis surface; a stat row over a list a user visits to retrieve one specific thing is decoration.
If the archive grows past a screenful, a search field is the first thing to add — and `SearchField`
already exists for it, at no design cost. Not now.

(matching `ParcelasTable`, where the ID column is also first) and `Ações` last (matching
`ParcelasTable`). `Valor` is `text-right tabular-nums`, per both existing tables.

### Dialogs

Both new dialogs use `AlertDialogContent` at its default size (`max-w-xs` mobile,
`sm:max-w-sm` desktop). Reading order in both: title → what happens → the caveat/warning → actions.
The warning line always sits **above** the footer, never inside it — the footer is for decisions, not
information.
